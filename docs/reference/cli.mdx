The `skyvern` CLI gives you direct access to browser automation, agent management, credential storage, and more, all from your terminal. Use it in shell scripts, CI/CD pipelines, or for quick one-off tasks.

## Install

```bash
pip install skyvern
```

The `skyvern browser …`, `skyvern setup` and `skyvern mcp …` commands also need the local extra (it adds Playwright and the config libraries those commands use):

```bash
pip install "skyvern[local]"
```

`skyvern run server` and `skyvern run mcp` need the server extra instead, which includes everything in the local extra:

```bash
pip install "skyvern[server]"
```

Set your API key and target:

```bash
export SKYVERN_API_KEY="YOUR_KEY"  # get one at https://app.skyvern.com
export SKYVERN_BASE_URL="https://api.skyvern.com"  # or your staging / self-hosted URL
```

With an API key present, the CLI refuses to fall back to the production URL silently — `SKYVERN_BASE_URL` must name your target explicitly.

Optionally run the interactive setup wizard to configure your environment:

```bash
skyvern init
```

## Command reference

### Services

```bash
skyvern run server            # Start the local API server
skyvern run ui                # Start the local UI on port 8080 (--force stops whatever already uses the port)
skyvern run all               # Start the API server and the UI together, in this terminal
skyvern run dev               # Start the API server and the UI in the background and return
skyvern run docker            # Run docker compose up -d with the docker-compose.yml in this directory
skyvern run mcp               # Start the MCP server (stdio transport)
skyvern run mcp --transport streamable-http  # Start the MCP server (HTTP transport)
skyvern run code --params-file params.json main.py  # Run a Skyvern Python script with parameters from a JSON file
skyvern run code -p name=value main.py              # Or one -p per parameter, or --params with a JSON string
skyvern status                # Check if services are running
skyvern stop all              # Stop whatever listens on ports 8000, 8080 and 9090
skyvern stop server           # Stop whatever listens on the API port (--port, default 8000)
skyvern stop ui               # Stop whatever listens on ports 8080 and 9090
skyvern stop docker           # Stop the Docker Compose services
```

`run ui`, `run all` and `run dev` need the UI's source, which a `pip install` doesn't include. Use a source checkout or Docker Compose for the UI. On a `pip` install, `run all` starts only the API server.

`run code` takes its options before the script path. After the path, they are rejected.

`stop all`, `stop server` and `stop ui` don't check that a process on those ports is Skyvern's, so they also end any other program listening there.

### Browser automation

All browser commands operate on an active session. Create one first, then run actions against it.

```bash
# Browser session management
skyvern browser session create              # Start a cloud browser session
skyvern browser session create --timeout 30 # Custom timeout (minutes)
skyvern browser session list                # List active sessions
skyvern browser session get --session pbs_xxx
skyvern browser session connect --cdp ws://localhost:9222  # Connect to local Chrome
skyvern browser session close               # Close the active session

# Navigation
skyvern browser navigate --url https://example.com

# AI-powered actions
skyvern browser act --prompt "Click the Sign In button"
skyvern browser extract --prompt "Get all product names and prices"
skyvern browser validate --prompt "Is the user logged in?"

# Precision actions (CSS/XPath selectors or natural language intent)
skyvern browser click --selector "#submit-btn"
skyvern browser click --intent "the checkout button"
skyvern browser type --selector "#email" --text "user@example.com"
skyvern browser select --selector "#country" --value "US"
skyvern browser scroll --direction down --amount 500
skyvern browser press-key --key Enter
skyvern browser hover --selector ".menu-item"
skyvern browser wait --selector "#results" --state visible

# Screenshots
skyvern browser screenshot
skyvern browser screenshot --full-page --output page.png

# Run JavaScript
skyvern browser evaluate --expression "document.title"

# Full task automation (multi-step agent)
skyvern browser run-task --prompt "Find the cheapest flight from NYC to LA"
skyvern browser login --url https://app.example.com --credential-id cred_xxx

# One-shot QA: creates a cloud session, runs the task, returns the result with recording links, closes the session.
# It exits 0 even when the task fails, so check the status it prints (with --json, the top-level status).
skyvern browser qa "Log in and check the dashboard" --url https://app.example.com

# Read the page (these read the main frame, even after frame switch)
skyvern browser get-html "#main"            # innerHTML; --outer for outerHTML
skyvern browser get-value "#email"          # Current value of a form field
skyvern browser get-styles ".banner" color font-size  # Computed styles; omit the names to get all (at most 100)
skyvern browser find role button            # Playwright locators: role, text, label, placeholder, alt or testid

# Frames
skyvern browser frame list
skyvern browser frame switch --selector "iframe#checkout"  # Or --name, or --index (0 is the main frame)
skyvern browser frame main                  # Back to the main frame

# Sign-in state, storage and clipboard
skyvern browser state save auth.json        # Cookies, plus this page's localStorage and sessionStorage
# auth.json can sign in as you. Keep it out of version control.
# state load writes storage to the open page and doesn't check its origin,
# so first open a page with the saved page's scheme, host and port.
skyvern browser state load auth.json
skyvern browser storage get-session         # Prints keys and values, which can hold session data. Name keys to limit it
skyvern browser storage set-session theme dark
skyvern browser storage clear-session
skyvern browser storage clear-local
# The clipboard commands ignore the saved session, so pass --session or --cdp.
# They need an HTTPS or localhost page.
skyvern browser clipboard-write "text to paste" --session pbs_xxx
skyvern browser clipboard-read --session pbs_xxx
```

The `skyvern browser extension-*` commands set up the Skyvern Agent Chrome extension. See [Share tabs with a local MCP server](/browsers#share-tabs-with-a-local-mcp-server).

The `skyvern browser network` commands (`requests`, `detail`, `route`, `unroute`), `har-start`, `har-stop` and `get-errors` don't work as separate shell commands. They keep captured requests, routes, the HAR recording and page errors in the memory of the process that runs them, and each `skyvern` command is a new process. So `network requests` starts empty, `har-stop` after a `har-start` reports no active recording, `get-errors` reports no errors even when the page threw some, and a route stops applying when its command exits.

To capture or mock traffic, or read page errors, across several steps, run a [local MCP server](/developers/getting-started/mcp#run-the-server-locally-stdio), attach it before the action, and use its `skyvern_network_*`, `skyvern_har_*` and `skyvern_get_errors` tools in one session. Mock and abort cover the top-level page and same-process frames, not out-of-process cross-site iframes. The hosted MCP server keeps no state between requests, so those tools return an error there.

<Tip>
Most browser commands support `--json` for machine-readable output. Commands that act on a page also take `--session` or `--cdp` to target a specific session. If you omit both, the CLI uses the session saved by `session create` or `session connect`, for up to 24 hours. `clipboard-read`, `clipboard-write`, `har-start`, `har-stop` and `get-errors` ignore the saved session and always need one of the two.
</Tip>

### Connect your local browser to Skyvern Cloud

Expose your local Chrome to Skyvern Cloud so tasks can access localhost, internal tools, and your existing login sessions.

```bash
# Launch with ngrok tunnel and your Chrome profile's cookies/logins
skyvern browser serve --tunnel --use-local-profile

# Use a specific Chrome profile
skyvern browser serve --tunnel --use-local-profile --chrome-profile-name "Profile 2"

# Headless mode (--json cannot be combined with --tunnel)
skyvern browser serve --tunnel --headless
```

The `--use-local-profile` flag clones cookies and saved passwords from your Chrome profile into the served browser. Your original profile is never modified, and it works while Chrome is open.

<Warning>
Always pass `--api-key` when using `--tunnel`. Without it, anyone with the ngrok URL has full browser control.
</Warning>

See the [full guide](/browsers#let-cloud-runs-use-your-chrome) for all options, manual tunnel setup, and security details.

### Agents

```bash
skyvern workflow list                              # List all workflows
skyvern workflow get --id wpid_xxx                 # Get workflow details
skyvern workflow create --definition @workflow.json  # Create from a JSON/YAML file (or inline string)
skyvern workflow update --id wpid_xxx --definition @updated.json
skyvern workflow delete --id wpid_xxx --force       # --force confirms the permanent delete
skyvern workflow run --id wpid_xxx                  # Execute a workflow
skyvern workflow run --id wpid_xxx --params '{"url": "https://example.com"}'
skyvern workflow run --id wpid_xxx --wait --timeout 600  # Return when the run finishes (--timeout in seconds, default 300)
skyvern workflow runs --id wpid_xxx                 # List runs of a workflow (--status, --search-key, --error-code, --page, --page-size)
skyvern workflow status --run-id wr_xxx              # Check run status
skyvern workflow cancel --run-id wr_xxx              # Cancel a running workflow
skyvern workflow retry --run-id wr_xxx               # Retry a finished workflow run
skyvern tasks list --workflow-run-id wr_xxx          # List the tasks of a workflow run (the 100 newest)
```

### Schedules

```bash
skyvern schedule list                                # List all schedules (--status active|paused, --search, --page, --page-size)
skyvern schedule list --workflow-id wpid_xxx         # List the schedules of one workflow
skyvern schedule get --workflow-id wpid_xxx --id wfs_xxx
skyvern schedule create --workflow-id wpid_xxx --cron "0 9 * * *" --timezone America/New_York
skyvern schedule create --workflow-id wpid_xxx --interval-seconds 259200  # Every 72 hours (minimum 300)
skyvern schedule update --workflow-id wpid_xxx --id wfs_xxx --cron "0 10 * * *"
skyvern schedule enable --workflow-id wpid_xxx --id wfs_xxx
skyvern schedule disable --workflow-id wpid_xxx --id wfs_xxx
skyvern schedule delete --workflow-id wpid_xxx --id wfs_xxx --yes  # --yes is required
```

`schedule create` also takes `--parameters` (JSON object), `--name`, `--description`, `--first-fire-at` and `--disabled`. The default timezone is `UTC`.

### Organization settings

```bash
skyvern config show                          # Show all organization settings
skyvern config get max_steps_per_run         # Show one setting
skyvern config set max_steps_per_run 25      # Change one setting
```

`config set` accepts `max_steps_per_run`, `max_steps_per_workflow_run`, `max_retries_per_step`, `webhook_callback_url`, `artifact_url_expiry_seconds` (3600 to 604800), `slug`, `default_llm_key` and `default_secondary_llm_key` (custom LLM keys for the Smart and Fast models), and the reset flags `clear_max_steps_per_workflow_run`, `clear_artifact_url_expiry_seconds`, `clear_default_llm_key` and `clear_default_secondary_llm_key`. `skyvern config set --help` prints the current list.

### Credentials

`skyvern credentials add` prompts for secret values so they never appear in shell history. In scripts or CI, set them as environment variables instead.

```bash
skyvern credentials add --name "Vendor portal"                       # Password (default type); prompts for username, password, TOTP
skyvern credentials add --name "Company card" --type credit_card     # Prompts for card number, CVV, expiry, brand, holder name
skyvern credentials add --name "Portal API key" --type secret        # Prompts for the secret value and an optional label
skyvern credential list            # List stored credentials
skyvern credential get --id cred_xxx
skyvern credential delete --id cred_xxx
```

`--name` is required. `--type` is `password` (default), `credit_card` or `secret`.

| Type | Environment variables |
|---|---|
| `password` | `SKYVERN_CRED_USERNAME`, `SKYVERN_CRED_PASSWORD`, `SKYVERN_CRED_TOTP` |
| `credit_card` | `SKYVERN_CRED_CARD_NUMBER`, `SKYVERN_CRED_CVV`, `SKYVERN_CRED_EXP_MONTH`, `SKYVERN_CRED_EXP_YEAR`, `SKYVERN_CRED_CARD_BRAND`, `SKYVERN_CRED_HOLDER_NAME` |
| `secret` | `SKYVERN_CRED_SECRET_VALUE`, `SKYVERN_CRED_SECRET_LABEL` |

Note: `credentials` (plural) has `add`, `list`, `get` and `delete`; `credential` (singular) has only `list`, `get` and `delete`, matching the MCP tools. Both forms are intentional.

### MCP setup

Register Skyvern's MCP server with your AI coding tool in one command:

```bash
skyvern setup claude-code             # Auto: .mcp.json in a project, ~/.claude.json otherwise
skyvern setup claude-code --project   # Force project-local Claude Code config
skyvern setup claude-code --global    # Force global Claude Code config
skyvern setup claude                  # Register with Claude Desktop
skyvern setup cursor             # Register with Cursor
skyvern setup windsurf           # Register with Windsurf
skyvern setup openclaw           # Register with OpenClaw
skyvern setup opencode           # Register with OpenCode (API key auth; avoids OAuth timeouts)
skyvern setup hermes             # Register with Hermes (~/.hermes/config.yaml and each profile that has a config.yaml)
skyvern setup mcporter           # Show which configs have a Skyvern entry for MCPorter to find (writes nothing)
skyvern mcp switch                    # Interactively switch existing Skyvern MCP configs
skyvern mcp switch --dry-run          # Preview changes without writing files
skyvern mcp profile list              # List saved switch sources
skyvern mcp profile save work-prod --api-key YOUR_KEY --base-url https://api.skyvern.com
```

For the local self-hosted path, `skyvern quickstart` or `skyvern init` can also configure Claude Code during the interactive MCP step. In a project directory that flow writes `.mcp.json`, installs the bundled skills (including `/qa`) into `.claude/skills/`, and keeps the MCP connection fully local for localhost testing.

For Skyvern Cloud in Claude Desktop, use **Customize > Connectors > Add custom connector**, enter `https://api.skyvern.com/mcp/`, and sign in with your Skyvern account. This path needs no API key or local Node.js installation. For API-key setups, the downloadable `.mcpb` bundle on macOS and Windows remains an alternative. `skyvern setup claude` writes a direct Node.js configuration for the bundled API-key adapter (SDK 2.3.1), without `npx` or npm installation; Node.js 20.18.1 or later is required. See [MCP and coding agents](/developers/getting-started/mcp).

`skyvern mcp switch` updates existing Skyvern entries in Claude Code, Claude Desktop, Cursor, Windsurf, Codex, Hermes, OpenClaw, and OpenCode configs. It lets you choose a source from env, saved profiles, existing configs already on disk, or manual entry; creates backups before writing; and preserves the config's current transport shape. If a tool has no Skyvern entry yet, run `skyvern setup` first.

### Other

```bash
skyvern docs                     # Open documentation in your browser
skyvern login                    # Sign in to Skyvern Cloud in your browser and save the API key (--base-url, --timeout)
skyvern capabilities workflow    # The command tree as JSON, for agents; omit the group for all (--depth 0 to 5, default 1)
skyvern quickstart               # One-command setup + start
skyvern init                     # Interactive setup wizard (does not start the Skyvern server)
skyvern init browser             # Initialize browser configuration only
skyvern doctor                   # Check the installation (--fix tries to repair what fails)
skyvern doctor streaming         # Check that local browser streaming works (--base-url, --browser-session-id, --timeout)
```

For a local server, `skyvern init` uses PostgreSQL if it is already running, or offers to start a container in Docker (`--no-postgres` skips the offer, and `--database-string` points it at your own database). It then runs the database migrations. Start Skyvern afterwards with `skyvern run server`.

## CLI vs MCP: when to use which

| Use case | CLI | MCP |
|----------|-----|-----|
| Shell scripts and CI/CD | Yes | No |
| One-off browser tasks | Yes | Yes |
| AI assistant integration (Claude, Cursor, Codex) | No | Yes |
| Credential creation (secrets via stdin) | Yes | No |
| Starting/stopping services | Yes | No |
| Composing with Unix pipes (`--json` output) | Yes | No |
| Natural language orchestration by an AI agent | No | Yes |

The CLI and MCP server share the same underlying logic. The CLI is for humans and scripts; MCP is for AI assistants that call tools programmatically.

## Skills

Skills are bundled reference markdown files that teach AI coding tools how to use Skyvern. They are **not** the same as MCP tools; they are documentation that an AI agent can load to learn the CLI and API.

```bash
skyvern skill list                  # List available skills
skyvern skill show skyvern          # Render a skill in the terminal
skyvern skill path skyvern          # Print the absolute path to a skill file
skyvern skill path                  # Print the skills directory
skyvern skill copy --output ./docs  # Copy all skills to a local directory
skyvern skill copy skyvern -o .     # Copy a single skill
skyvern skill post-qa-report        # Post or update .qa/latest-report.md as a comment on the current branch's open PR (needs gh)
```

<Accordion title="Loading skills into AI tools">

Skills are plain markdown files. You can load them into any AI coding tool that supports custom instructions:

**Claude Code**: the recommended local path is `skyvern quickstart` or `skyvern init`, then choose Claude Code during MCP setup. That writes `.mcp.json` and installs bundled skills like `/qa`. You can also run `skyvern setup claude-code` later if you are configuring MCP separately.

**Codex**: copy the skill into your project's `.codex/skills/` directory:

```bash
skyvern skill copy skyvern -o .codex/skills/
```

**Hermes**: copy the skill to your active Hermes profile's skills directory. The skill needs Hermes-compatible frontmatter (`metadata.hermes.requires_tools` instead of `allowed-tools`):

```bash
# Create the skill directory
mkdir -p ~/.hermes/profiles/<your-profile>/skills/skyvern-browser-automation

# Copy the skill body (you'll need to replace the frontmatter; see below)
skyvern skill copy skyvern -o /tmp/skyvern-skill
```

The copy lands in `/tmp/skyvern-skill/skyvern/`. Replace the frontmatter in its `SKILL.md` with:

```yaml
---
name: skyvern-browser-automation
description: "Browser automation via Skyvern: scrape pages, fill forms, extract data, run workflows."
metadata:
  hermes:
    tags: [browser, automation, skyvern]
    requires_tools: [terminal]
---
```

Then move it into place: `cp /tmp/skyvern-skill/skyvern/SKILL.md ~/.hermes/profiles/<your-profile>/skills/skyvern-browser-automation/SKILL.md`

Verify with `hermes skills list | grep skyvern`.

<Tip>
When both the Skyvern MCP server and the CLI skill are configured, Hermes prefers MCP tools over shelling out to the CLI, which is faster. The skill's judgment procedure (task classification, step ordering) works with either execution path.
</Tip>

**OpenClaw**: copy the skill into your OpenClaw workspace `skills/` directory. By default that workspace lives at `~/.openclaw/workspace/`, but if you've customized the workspace path, use that location instead.

```bash
mkdir -p ~/.openclaw/workspace/skills
skyvern skill copy skyvern -o ~/.openclaw/workspace/skills/
openclaw skills list | grep skyvern
```

<Tip>
OpenClaw's MCP config provides the callable Skyvern tools; the workspace skill is optional guidance that teaches the agent when to use them.
</Tip>

**Any tool**: point your tool at the file path returned by `skyvern skill path skyvern`.

</Accordion>

## JSON output

The `browser`, `workflow`, `schedule`, `config`, `credential`, `credentials`, `block`, `tasks`, `status` and `stop` commands, and `doctor streaming`, take `--json` for structured output you can pipe to `jq`. The `skill`, `setup`, `mcp`, `run`, `init`, `quickstart` and `docs` commands, and plain `doctor`, do not. The output is an envelope (`ok`, `action`, `data`, `error`, …), and the command's result is under `data`. `browser qa` is the exception once its task runs: it prints its fields (`status`, `output`, `failure_reason`, …) at the top level, with no envelope. If the command fails before the task runs, for example when the session can't be created, it prints the usual envelope with `error` and exits 1.

```bash
# Extract the session ID from a new session
SESSION=$(skyvern browser session create --json | jq -r '.data.session_id')

# Extract data and pipe to a file
skyvern browser extract --prompt "Get all links" --json | jq '.data.extracted' > links.json

# Check workflow run status in a script
STATUS=$(skyvern workflow status --run-id wr_xxx --json | jq -r '.data.status')

# browser qa exits 0 even when the task fails, so check its top-level status
STATUS=$(skyvern browser qa "Log in and check the dashboard" --url https://app.example.com --json | jq -r '.status')
[ "$STATUS" = completed ] || { echo "QA did not pass: $STATUS"; exit 1; }
```

## Troubleshooting

<Accordion title="Command not found: skyvern">
Make sure the package is installed and on your PATH:

```bash
pip install skyvern
which skyvern
```

If using a virtual environment, activate it first. You can also run via module:

```bash
python3 -m skyvern --help
```
</Accordion>

<Accordion title="Authentication errors">
Verify your API key is set:

```bash
echo $SKYVERN_API_KEY
```

You can also pass it directly:

```bash
skyvern credentials --api-key YOUR_KEY add --name "Vendor portal"
```

Get an API key from [Settings](https://app.skyvern.com/settings/) in the Skyvern dashboard.
</Accordion>

<Accordion title="No active browser session">
Browser commands require an active session. Create one first:

```bash
skyvern browser session create
```

Or specify a session explicitly:

```bash
skyvern browser navigate --url https://example.com --session pbs_xxx
```
</Accordion>
