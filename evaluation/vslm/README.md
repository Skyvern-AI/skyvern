# V-SLM relevance filter — evaluation

An optional relevance filter that shrinks the free-text portion of Skyvern's
extraction prompts by dropping sentences a third-party sentence classifier
(ZettaQuant V-SLM) judges irrelevant to the extraction goal.

**This branch is an evaluation, not a proposed feature.** It is published so the
vendor can reproduce a recall problem we hit while testing. The filter is off by
default (`ENABLE_VSLM_TEXT_FILTER=False`) and fails open, so with the flag unset
none of this code runs.

## The finding

The classifier drops sentences whose relevance is carried by an **identifier**.
`Invoice #: 88213-B` scores 0.020 against the topic `invoice number`; the same
fact written as narrative prose (`Account number 4471-99823-01 is enrolled in
paperless billing.`) scores 0.990 against `account number`.

For document extraction this is the wrong failure mode: labelled identifiers are
exactly what users pull out of invoices, statements, and forms.

## Reproduce

Both scripts need a ZettaQuant API key:

```bash
export ZQ_API_KEY=<key>
```

### 1. API-level (no Skyvern setup, no dependencies)

```bash
python evaluation/vslm/repro_api.py
```

Pure `urllib`, Python 3.8+. Four parts: identifier vs narrative sentences,
one case across every topic-specification mode, the same case across all seven
agents, and an identifier buried in a realistic document.

### 2. End-to-end through Skyvern (needs a configured LLM provider)

```bash
python evaluation/vslm/repro_extraction.py
```

Drives the real `FileParserBlock._extract_with_ai()` — the method a production
FileParser block calls — over `sample_remittance_advice.txt`, once with the
filter off and once on. No database, no browser.

Expected output:

```
--- ENABLE_VSLM_TEXT_FILTER=false (baseline) ---
  OK    invoice_number     expected ~'88213-B', got '88213-B'
  OK    total_amount_due   expected ~'48,215.60', got '$48,215.60'
  OK    purchase_order     expected ~'PO-77213', got 'PO-77213'

--- ENABLE_VSLM_TEXT_FILTER=true ---
  block FAILED: LLM response does not match file parser JSON schema:
                root.invoice_number: expected type string, got null
```

The filter removes `Invoice #: 88213-B` before the prompt is built, so the model
returns `null` for `invoice_number`. Because `FileParserBlock` validates the
response against `json_schema`, that becomes a hard block failure after retries.
With a nullable field it would instead degrade silently.

## Settings

| Setting | Default | Notes |
|---|---|---|
| `ENABLE_VSLM_TEXT_FILTER` | `False` | Master switch; nothing runs when false |
| `ZQ_API_KEY` | `""` | Filter is skipped when empty |
| `ZQ_BASE_URL` | `https://api.zettaquant.ai` | |
| `VSLM_AGENT` | `general_context_agent` | One of the vendor's seven agents |
| `VSLM_TIMEOUT_SECONDS` | `30.0` | |
| `VSLM_MAX_ATTEMPTS` | `3` | Retries 429/5xx only, never 4xx |
| `VSLM_BACKOFF_SECONDS` | `0.5` | Exponential |

## Wiring

- `skyvern/utils/vslm_filter.py` — sentence split, batching (512/call), retry, fail-open
- `skyvern/webeye/actions/handler.py` — `extract_information_for_navigation_goal()`, filters `extracted_text`
- `skyvern/forge/sdk/workflow/models/block.py` — `FileParserBlock._extract_with_ai()`, filters parsed file text

`FileParserBlock` has no natural-language goal, only a target schema, so
`schema_to_query()` flattens the schema's field names and descriptions into a
topic string. The finding above is not an artifact of that helper — a
hand-written topic, the bare field name, and a topic generated by the vendor's
own `query` mode all produce the same drop (see `repro_api.py` part 2).

## Other measurements

Against the live API, warm path, measured while testing this branch:

- Latency is flat in batch size: 0.96s at 4 sentences, 1.14s at 512.
- Output is deterministic — byte-identical across five runs of the same input.
- 20/20 sequential calls succeeded; the first call of a session took 27.8s (cold start).
